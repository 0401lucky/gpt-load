# 捐献人工审核与真实调用测试

## Goal

让不能通过通用模型测试的渠道也能参与捐献：管理员按活动选择跳过自动模型测试，此时必须经过人工审核；在 new-api 捐献流程内提供针对该笔捐献 key 的真实调用工具，辅助判断是否接收和发放永久奖励。

## Requirements

- **R1 活动模式**：在 new-api 活动配置中增加“跳过模型测试，改为人工审核”开关，默认关闭。关闭时沿用自动测试；开启时以人工审核决定是否接收，不直接发奖。
- **R2 人工审核**：人工模式中的非重复合格提交进入待审核，key 加密暂存，尚不进入正式分组调度。管理员逐项通过或拒绝；拒绝需填写供捐献人查看的原因，通过可留备注。保留决定、操作者、时间和原因。
- **R3 真实调用入口**：仅管理员在 new-api 捐献审核详情内使用；从原目标分组选择支持文字对话的模型，输入用户提示词及可选系统提示词，设置有界输出，支持流式/非流式响应及停止。首版为单次对话测试，结果供人工参考；成功不自动通过，失败不自动拒绝，也不把一次成功测试设为人工通过的硬门槛。
- **R4 真实证据**：调用只能使用当前待审核 key，遵循已绑定组配置，不被其他 key/分组接替。结果关联捐献项、模型和目标配置；目标改变后旧测试明确失效，不用于当前配置的证明。
- **R5 接收与奖励**：人工审核通过、首次正式接收且运行时发布完成后，按受理时冻结的固定金额自动发放一次永久奖励。测试本身不扣捐献人或管理员的站内钱包余额，实际消耗该 key 的上游配额。保留全局防重、账号暂停、不限领奖数量和已发奖励不追回规则。
- **R6 状态呈现**：用户可区分待审核、审核拒绝、暂存过期、接收处理中、已接收和奖励状态；管理员可筛选待审核记录并查看测试与审核历史。混合批次逐项处理，等待人工审核不能表现为持续自动检测或已到账。
- **R7 规则兼容**：提交时冻结活动模式、版本、目标与奖励；更改活动只影响新批次，不静默改变历史。旧活动、旧自动批次及旧客户端保留原行为；远端缺少新能力时明确提示需升级，不能降级为无审核接收。
- **R8 秘密与权限**：浏览器不取得完整捐献 key 或服务间 token；记录读取权不隐含审核/测试写权限。普通用户不能调用审核/测试接口。模型输出作为不可信文本展示，流式和非流式输出、错误及审计不得泄露认证材料；完整对话不持久保存到浏览器或长期业务账本。
- **R9 动作恢复**：重复点击、并发管理员、网络响应丢失及进程重启不能重复执行审核、入库或奖励；旧结果不能覆盖新决定。真实调用中断不自动重新发送模型请求，可重新发起新的测试。
- **R10 旧失败记录**：仍在暂存期内、自动测试已耗尽且未接收的记录，允许管理员显式“转人工审核”，无需再次复制 key。保留原批次、捐献人、奖励、请求身份与原始提交模式，并另外记录这次转审；不自动转换所有历史失败项。
- **R11 等待与过期**：沿用现有 7 天加密暂存期，转审或测试不续期。过期后不可再测试或通过、不发奖，用户可重新捐献；拒绝/过期只清理暂存材料，保留历史记录和已取得资源的永久去重事实。
- **R12 目标异常**：目标被删除、禁用或人工审核期间配置变化时，停止测试/通过，保留拒绝入口；可以恢复原配置或拒绝后重新提交。首版不提供对原捐献重新选择组或静默绑定新配置的能力。

## Acceptance Criteria

- [ ] **AC1 → R1/R7**：旧活动/旧客户端仍自动测试，旧接收端未提供新版本字段的合法自动状态仍可推进；人工模式可保存并用于新提交，刷新或重启不改变模式。缺少新能力时不能启用人工模式。
- [ ] **AC2 → R2/R5**：新人工项等待审核时没有正式凭据、没有奖励；通过后仅首次入库项发一次原定永久奖励，拒绝不入库、不发奖并展示原因。
- [ ] **AC3 → R3/R4/R5**：真实 HTTP 对话测试收到原 key、选中模型和输入文本；即使库存有可用 key，待测 key 失败也不能切换成功。流式及非流式结果可见，站内钱包不扣费。
- [ ] **AC4 → R3**：测试成功后仍待人工决定；失败后不自动拒绝，具有审核权限的管理员可依据其他证据通过。
- [ ] **AC5 → R5/R9**：并发通过/拒绝、重复动作、接收或发奖响应丢失、两端重启均不重复入库/发奖；没有可信人工通过事实的 accepted 回执不能为人工项发奖。
- [ ] **AC6 → R2/R6/R8**：普通用户/仅记录只读管理员不能测试或审核；捐献人通过本人批次详情看到已确认拒绝原因，不能读取他人备注或管理测试详情；混合批次正确区分待审核与处理中的其他项。
- [ ] **AC7 → R8**：测试中上游回显完整 key（含跨流片段）不会泄露到 UI/日志；切换记录/账号、退出或关闭详情后旧响应不能出现在新页面。
- [ ] **AC8 → R9**：停止、断流和进程中断产生明确结果，不把部分回复标成完整成功，不自动发送第二次模型调用。
- [ ] **AC9 → R10**：有效暂存的旧 retry_exhausted 项可显式转审，保留原批次及固定奖励；转审与旧 worker 并发不自动接收、不重写旧幂等摘要。
- [ ] **AC10 → R11**：待审核超过原暂存期限后不可测试/通过且不发奖；释放未接收资格后允许新提交，原历史和已接收去重仍保留。
- [ ] **AC11 → R4/R12**：目标变化使旧测试失效、测试/通过被拒绝；目标下线或删除时仍可拒绝，不会改投其他组。
- [ ] **AC12 → R5/R7**：自动模式的有效/无效/重复/已有 key、删除后防重、固定永久奖励、账号暂停、历史恢复全部保持兼容。
- [ ] **AC13 → R7/R9**：两端数据库支持新建、含真实旧捐献数据的升级及重复迁移；旧自动批次请求重放不冲突，不重置身份或奖励账本。
- [ ] **AC14 → R6/R9**：待审核记录不占满自动恢复工作队列；用户页面不因长期待审而持续快速轮询，操作完成后能刷新到最新状态。

## Out of Scope

- 捐献人自测、通用聊天应用、多轮持久会话、图片/音频/视频测试、Coding Agent/工具执行、任意 URL/原始请求 JSON/认证头编辑。
- 自动追回永久奖励、新增用户/每日领奖数量上限、修改签到或其他钱包政策。
- 自动改变历史模式、重新指定接收组、对暂存过期材料恢复明文、绕过上游限制。
- 生产部署、真实上游验收、凭据或全局配置变更、外部发布；这些不属于本地实现授权。

## Known Limits

- 真实对话测试更接近日常调用，仍可能被特定上游限制；失败只代表该次请求结果，不证明 key 在其他允许场景下一定不可用。
- 首版文字对话只覆盖所选分组当前执行器支持的文本模型；没有兼容模型时仍可人工核实，但界面不能伪造可运行的测试入口。
- 人工批准意味着管理员承担判断责任，后续 key 失效不追回奖励；已过期暂存 key 需要捐献人重新提供。
- 详细设计与验证计划分别在 `design.md`、`implement.md`；首轮证据在 `research/feasibility.md`，后续两端复核与 UI 约定在本任务 `research/`。
