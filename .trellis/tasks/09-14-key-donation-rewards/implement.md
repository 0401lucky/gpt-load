## 防重复与记录保留专项验收

| 场景 | 必须满足的结果 |
| --- | --- |
| 原提交直接重试或超时后重试 | 查询/恢复同一明细与回执，至多一次奖励 |
| 换新请求 ID、用户、活动或组提交同一 key | 命中长期资源身份，不产生第二笔奖励 |
| 两个不同用户并发提交同一 key | 唯一资格只归属一次成功接收；不能两边都领到奖励 |
| 上游返回无效、限流、超时，或接收失败 | 不发奖；保留失败/待处理明细，与已接收记录区分 |
| 多行混合新有效、重复、已有和无效 key | 逐条处理，新有效项正常奖励；重复/已有/无效项不发奖且不阻断其他项 |
| 一个批次处理到一半重启 | 按原明细 ID 恢复，已成功部分不重发，未决部分先查回执 |
| gpt-load 接收成功但 new-api 未收到回执 | 先按原标识对账，不释放为另一次新资源提交 |
| 已奖励 key 失效、禁用、删除或所在组删除 | 永久奖励不追回，来源、指纹和奖励历史保留，再提交不恢复资格 |
| 普通日志清理或控制面操作结果压缩 | 不清除业务去重与原接收/奖励历史 |
| 同一用户同日提交多个不同的合格 key | 按单 key 固定规则分别奖励，不设置每日领奖数量门禁 |
| 发奖后跨日或运行签到过期清理 | 未消费的永久奖励保留，不写入签到临时桶 |
| 同项目的不同 Gemini key | 首版以 key 判断，不设领奖数量上限，也不宣称已验证项目独立配额 |
