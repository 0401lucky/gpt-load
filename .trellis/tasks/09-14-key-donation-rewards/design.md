# 捐献功能技术设计

> 最终审阅版 v1 · 2026-09-14。需求以 [PRD](prd.md) 为准；接口、逻辑数据约束和恢复协议统一见 [集成契约 v1](research/integration-contract.md)。续接已获本地实施授权，进度与验证证据见 [progress.md](progress.md)。

## 页面位置与系统分工

| 职责 | 归属 | 说明 |
| --- | --- | --- |
| 捐献入口与用户页面 | new-api | 顶部导航提供入口，复用现有用户会话；查看活动、提交 key 和查询本人结果 |
| 活动配置与分组选择 | new-api | 管理员在站内配置名称、规则、目标组和开关；通过后端加载 gpt-load 分组 |
| 用户来源、管理记录和奖励 | new-api | 保存用户与每个捐献项的关联；由站内业务服务执行奖励结算与恢复 |
| 分组、上游协议和密钥 | gpt-load | 提供受限的分组查询、密钥校验、接收及接收结果查询能力 |

用户路径：`顶部导航「捐献」→ 现有账号登录/身份确认 → 选择活动并提交 → 查看校验、接收和奖励结果`。页面具体路由名在实施时按 new-api 现有结构确定。

key 输入框附近显示 PRD R18 的风险小字，提交前可见，明确不要使用主账号，以及账号受限/封禁、key 失效风险。采用现有辅助文字样式并保持可读性，移动端正常换行；不增加弹窗、勾选确认或其他额外门槛。

复用 `useTopNavLinks` 和现有 `HeaderNavModules` 导航配置，兼顾公共页顶栏、登录后顶栏及移动端入口。作为内建功能加入捐献导航项，并兼容旧配置缺省值；不要求管理员额外手填自定义链接。导航显示状态不能替代后端参与和管理权限检查。

身份由 new-api 的认证上下文确定，沿用现有登录资格，不额外增加 Linux DO 绑定门槛。无需 gpt-load 新建社区用户会话、另接 Linux DO OAuth 或调用 new-api 的管理查用户接口。gpt-load 接收来自已认证集成方的关联标识，不把用户提交的昵称或 ID 当作认证依据。

服务间通过受限的后端接口通信，不共享数据库。new-api 主动调用 gpt-load 并查询接收结果，gpt-load 无需持有 new-api 的管理员权限或调用其发额度接口。

## 活动配置

活动实体放在 new-api，引用已连接 gpt-load 的稳定实例标识与 `group_id`。基础配置是显示名称、目标分组、说明和开关；渠道、上游地址、密钥格式及验证协议/模型全部从分组与既有渠道能力解析。管理员管理真实分组仍使用 gpt-load 的现有能力，new-api 只维护捐献活动与目标组映射。

当前活动示例：

| 配置 | 内容 |
| --- | --- |
| 显示名称 | `gemini aistudio free key` |
| 入库分组 | 从 gpt-load 列表选择站长已配置好的 Gemini 组 |
| 奖励 | 每个有效非重复 key 一笔固定永久额度，金额由活动配置；不设到期时间或领奖数量上限 |
| 开启捐献 | 活动开关 |

不增加独立的「平台」下拉框、上游地址或测试模型输入项。名称只是展示文案，不能用名称中的 Gemini/free 等字样选择渠道、判定计费层级或计算奖励。首批验收针对 Gemini AI Studio，但 new-api 的表单与请求协议不写死 Gemini 专属参数；未来其他普通 key 分组继续遵循同一配置方式，具体支持以 gpt-load 能力和后续验证为准。

校验复用 gpt-load 的 `buildGroupValidationTarget`：优先使用组内验证模型，未设置时沿用其已有的组模型回退；协议来自组设置或渠道首选协议。若最终无法解析可用校验目标，应提示在 gpt-load 完善该组，而不是在 new-api 再维护一份参数。

分组选择器的设计：

- new-api 后端读取 gpt-load 的分组目录。已有 `/api/groups/options` 可复用查询逻辑，但集成访问需限定权限，不能把管理 token 交给捐献人。
- 向管理 UI 投影必要字段：组 ID、名称、渠道、连接类型、启用状态、能否接收普通 key/解析验证目标及不可选原因。渠道和类型用于只读说明，选择分组已经完成资源类型选择；无需转发原始 `params` 或完整组详情。
- 支持加载、刷新、空列表和连接失败状态；读取失败不能伪装成无分组，刷新失败不能静默改选其他组。
- 保存活动与正式接收前都核对目标组。被删除、禁用或类型不匹配的组不能继续接收；保留原选择和清晰提示，避免落入同名的另一个组。
- 以稳定 ID 绑定，以名称显示并保存历史快照；组改名不改变映射。新建的空组可以接收捐献，不能因为目前没有可用 key、运行状态是 unavailable 就过滤掉。

集成连接配置由管理员维护，服务地址与访问凭据由 new-api 后端使用。写入的秘密配置不回显，捐献页面不接触连接凭据；实际生产配置在上线准备阶段另行操作。

自动奖励采用活动配置的单 key 固定永久额度。金额是运营配置，不需要在规划阶段写死；页面无需提供永久/限时切换或有效期输入。首版不增加每日/每人领奖数量或活动累计奖励配额配置，合格的不同 key 分别奖励；保留原有额度数值范围校验。只呈现产品需要的设置，不把内部 fingerprint、幂等键或协议字段展示给捐献人。

服务端通过活动绑定的分组解析渠道、上游地址与验证目标；new-api 不建立第二套服务商配置。用户只选公开活动并提交 key，不能通过参数指定任意上游地址、代理、实际分组或奖励金额。

活动在 new-api 保存规则版本；提交时冻结适用规则和目标身份，后续结算使用该版本。gpt-load 在校验与接收间核对目标组关键配置，避免按旧目标验证、向新目标接收。

## 接收与校验

建议先接受 key 到隔离的加密暂存区域，执行指定凭据的真实探测，再通过控制面正式接收和更新运行时。现有管理导入会直接设为 active，不应直接作为未经验证的公开捐献入口。

- 复用渠道解析、加密、探测执行和运行时更新逻辑；不另写一套上游调用适配。
- 首批使用现有 Gemini 模块的普通 `api_key` 输入与探测能力；没有将余额查询、免费/付费层级识别或独立 Gemini 适配器列为接收前置条件。
- 探测只使用正在捐献的 key，不允许调度器切换到组内其他正常 key 后将其判为通过。
- 使用指定上游与模型的真实调用结果，复用协议响应和错误分类；格式校验通过、列出模型或客户端声称成功均不能替代真实可用性校验。校验与接收均成功后才触发奖励。
- 外部网络请求不放在长时间持有的数据库写事务内；new-api 受理批次时核对活动状态并冻结规则，gpt-load 接收前重新检查目标配置版本与资源去重。关闭活动拒绝新受理批次，已受理项按冻结规则继续；目标组已删除或无法校验时显式失败，不改投其他组。
- `failed` 与 `inconclusive` 分开；后者按配置的有界重试或人工处理流程执行，不直接发奖。
- 校验并发、请求超时和单次报文大小遵循服务的工程边界，不作为累计领奖数量限制；支持多行粘贴并采用有界工作队列处理。
- 失败暂存密文的保留期限和清理规则在实施设计中明确，清理不能同时抹掉必要的奖励去重记录。

### 多行粘贴与部分成功

- 一个批次选择一个活动，所有条目绑定该活动的目标组与受理时规则快照。输入每行一个 key，同时支持 LF 和 CRLF，忽略空行，对非空行去除首尾空白并保留大小写。
- 每个输入条目保留原始行号和稳定明细 ID；相同规范化 key 只触发一次校验/接收，后续同值行标为重复并关联首个条目，不发第二次奖励。
- 单条格式错误、上游拒绝、已有资源或限流超时不取消其他正常条目。按条目保存处理结果并独立结算，不能复用现有管理导入“一条格式错误导致整次返回错误”的行为作为公开捐献契约。
- 受理成功后通过批次 ID 查询逐项进度；批次响应、查询和恢复都使用稳定明细 ID 关联回执，不靠数组返回顺序。受理成功必须有持久化依据，不能仅在进程内存中排队后即宣称已接收。
- 页面显示 key 掩码、原始行号、校验/接收结果和奖励状态，汇总成功、失败、重复、处理中及已到账额度；处理中不能算作成功或失败。失败原因不回显完整 key。
- 原批次重试与失败项重试都受请求和资源去重约束；已成功项不再次校验或发奖，未确定远端结果的条目先对账。单条提交就是只有一行的批次。

## 身份、去重与记录

new-api 主库存储活动、提交批次、逐 key 的捐献明细和奖励流水；gpt-load 保存可恢复的接收结果及凭据来源关联。每个 key 的身份、历史和奖励独立于批次汇总保存。

记录应能关联：服务端生成的提交/明细 ID、来源站点及 new-api 用户 ID、已验证的 Linux DO ID（如有）、活动与规则版本、资源身份、校验结果、gpt-load 实例/组/凭据 ID 和奖励业务单号。用户与组的名称仅作显示快照，不用昵称或 key 的可见前后缀做唯一关联。

当前 `CredentialImportResult` 只有新增/重复汇总数量，不足以完成 R12。应新增捐献专用的逐项接收回执，稳定返回捐献项 ID、接收状态和成功对应的凭据 ID；同请求重放得到同一关联结果。保留现有管理导入契约，不能通过猜测 ID、查询最近创建行或导入前后数量差来归属 key。

重复提交记录属于本次提交人，但不能覆盖已经接收的 key 的原始来源用户。组改名、凭据失效/删除以及用户改名后，历史记录仍可追溯；远端资源已不存在时标记状态，不静默改绑到其他资源。跨库使用逻辑关联，不创建跨数据库外键。

需要分别处理并以数据库约束兜底：

1. 请求重试：同一请求身份、相同内容返回原结果；相同身份却改变内容则拒绝。
2. 资源重复：本站普通 key 的奖励身份来自规范化后的完整 key 值，保留大小写、忽略约定的首尾空白；不取掩码、随机密文、用户/活动/组 ID 或上游地址作为唯一依据。同一 key 换目标、提交人或请求 ID 也只能获得一次奖励资格。
3. 业务入账：稳定的捐献资源身份与奖励业务单号都受唯一约束保护。同一资源不能通过创建新的业务单号获得第二次奖励，金额与奖励记录必须在同一个 new-api 主库事务中提交。

同一 key 历史接收后失效、禁用或删除，均不恢复资格。这一约束独立于正常调度中是否仍存在该凭据。

### 长期去重与并发边界

- new-api 保存独立于资源行生命周期的捐献资源指纹/接收资格记录，关联唯一成功明细。对普通 key 使用服务端持久密钥生成 HMAC 指纹，不在普通日志存明文；指纹格式有版本，重启、切换组和连接地址不能使历史身份失效。
- 指纹密钥独立于会话 token、连接访问凭据和活动设置；不得随这些配置轮换重置。备份恢复包含记录与对应密钥；未来变更指纹算法/密钥必须兼容旧记录，不能把所有旧 key 当成新资源。
- gpt-load 可以复用现有规范化、加密及 HMAC 能力做接收侧去重，但不能直接假定两个进程使用同一指纹密钥，或共享它们的加密主密钥。两边通过稳定捐献明细 ID 关联。
- 先查询用于快速拒绝已接收资源，正式资格占用和接收时仍依赖唯一约束与条件更新。不能依赖“先查没有、再插入”、单进程锁或前端禁用按钮来防并发。
- 新请求遇到相同 key 正在处理时，关联原处理中状态或返回处理中结果，不并行触发第二次奖励。临时占用需要明确处理归属；网络超时不能直接当作未接收并释放资格，必须先查询原回执。
- 确认未被接收的失败尝试保留明细，和已接收/已奖励的永久去重标记分开；失败处理不应错误地永久占据成功接收资格。重试继续遵守身份与有界校验策略。
- 接收记录、捐献来源和奖励标记没有随 key 状态变化的自动过期清理，也不随活动、组或凭据的删除级联消失。现有控制面操作结果可被压缩，因此不能用短期请求回放结果代替长期业务依据。

按照“首次新增、非重复才奖励”的已定规则，当前已在 gpt-load 库中的 key（包括管理端导入）返回已有资源，不发新捐献奖励，也不改写其原始来源。接收前检查与管理导入可能并发的窗口，不能只在批次受理时检查一次。现有资源不伪造捐献用户；不存在于任何历史记录中的已删除旧 key 不能声称可追溯。

### 不同 key 共享项目配额的边界

Google 官方说明 Gemini 限额按项目计算，不按 API key 单独分配，见研究记录第 8 节。因此严格的同 key 去重不能证明不同 key 带来了独立配额；当前凭据探测也没有返回可信 Google 项目身份。

用户明确决定首版不设领奖数量上限，认为当前捐献规模较小。页面、活动模型和结算流程不增加每日领奖计数或累计奖励配额门禁；按已确认的 key 去重及固定奖励规则执行。保留项目配额共享这一能力边界，不增加 Google 管理凭证或要求用户手填项目 ID 作为可信证明。

## 管理员捐献记录

在 new-api 管理端增加「捐献记录」视图，沿用现有日志的表格、分页、筛选和详情交互；业务数据来自持久捐献明细，常规日志清理不能移除来源和奖励去重依据。

记录展示字段：提交时间、用户/用户 ID、活动名称、key 脱敏标识、目标分组、gpt-load 凭据 ID、校验/接收状态、奖励额度和到账状态。详情页展示同一捐献项的处理过程与关联奖励流水。管理员可按用户、活动、分组、状态、时间及记录/凭据 ID 定位。

历史接收结果与后续凭据状态分开：原先通过校验、成功接收和已奖励的事实不可被后来的“失效/已删除”覆盖。需要展示当前状态时使用 gpt-load 的真实状态及观测时间，不为满足历史保留额外承诺一套定时全量测试。

完整 key 不写入普通日志或列表响应；日常识别使用掩码和稳定凭据标识，秘密资源继续使用 gpt-load 的既有保护能力。记录可包含失败或重复尝试，不能把这些尝试显示成成功新增的资源。

UI 优先复用 `@/components/data-table` 的 `DataTablePage`、`useDataTable` 及现有审计日志的筛选/详情组合模式。活动配置、管理记录和本人记录的权限由服务端分别控制；管理配置操作可额外写入既有审计，引用捐献记录 ID。

## 发奖与跨服务恢复

接收与奖励分开建模：gpt-load 的暂存/校验/提交/接收状态，以及 new-api 的待奖励/已奖励状态按集成契约流转；重复、已有、无效和待重试都明确显示，不能用一个“成功”覆盖所有阶段。

gpt-load 正式接收时，应在本地事务内保存凭据关联与可恢复的逐项接收结果。new-api 负责持久化协调任务，按同一提交标识查询 gpt-load 回执，收到可信接收结果后在站内触发奖励结算。

new-api 的内部业务服务在一个主库事务内完成“检查/创建奖励唯一记录 + 校验用户及金额 + 增加永久余额 + 标记已入账”。同单号同内容重放返回已提交结果；不同内容冲突拒绝。所选站内路线不需要新增对外发奖接口，也不需要从 gpt-load 调用管理额度接口。

永久余额落到 new-api `User.Quota` 对应的钱包路径。复用/兼容扩展现有事务内的安全增额逻辑，并让奖励唯一记录和余额变化共用该事务；不能先调用一个自行提交事务的管理调整方法，再单独标记奖励完成。余额上界、原子增量、提交后缓存同步和捐献审计保留。捐献业务流水单独记录，不伪造现金支付订单。

响应丢失时查询同单号，不另生成奖励请求。日志与缓存是提交后的派生状态，需要复用并核对现有缓存、预扣余额和审计机制，不能通过覆盖余额补偿或重放缓存增量造成重复入账。主库中的奖励流水作为可恢复依据；跨日志库写入不宣称与主库天然原子。

受限的集成身份仅拥有所需分组查询、资源校验/接收和回执查询权限；gpt-load 验证来源与目标范围，new-api 验证用户、规则及额度边界。捐献人浏览器不持有服务间凭据，也不能声明自己已通过校验。

已接收 key 后不因临时奖励故障而自动删除资源；保留待发奖记录并重试。账号在处理期间被禁用时暂停未发奖励、保留原归属和原因，不改发其他用户；恢复后仍按原业务单号继续处理。活动关闭拒绝新批次，不静默取消已受理批次的固定奖励承诺。

## 永久奖励与后续状态

每个首次通过校验、成功接收的非重复 key 获得一笔活动配置的固定永久额度，自动发放；不按后续调用次数或使用量追加结算。计奖方式不从分组名称或上游套餐推导。

奖励不设到期时间，不进入签到临时额度桶，不修改签到或临时额度过期清理。当天是否签到以及签到类型不影响捐献奖励的永久入账。

用户已明确不追回奖励。key 后续失效、被封禁、撤销或删除，只更新资源当前状态；不扣回已发永久额度，也不实现自动追扣任务或撤销奖励按钮。原奖励历史与已领奖标记保留，同一个 key 永远不能据此重新领奖。

## 兼容性、上线与回退

- 对现有分组、管理导入和用户登录采用增量能力，活动默认关闭，不迁移存量 key 为捐献记录。
- 两边发布通过集成能力检查确认兼容版本，再开启活动；生产配置与凭据变更单独在上线阶段确认。
- 回退优先关闭新提交、暂停相关 worker，保留已接收资源与奖励记录；不回滚已承诺/已发放额度，不删除去重账本。
- new-api 数据库变更遵守其真实三数据库验收要求；gpt-load 遵守现有迁移与控制面运行时契约。

没有未决产品问题。物理表名、迁移编号、秘密配置落点和有界重试时间由子任务按仓库约定落实并验证；这些内部选择不得改变 [集成契约](research/integration-contract.md) 中的权限、唯一性、状态和奖励行为。
