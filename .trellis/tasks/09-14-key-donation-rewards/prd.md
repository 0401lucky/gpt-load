# 密钥捐献与社区额度奖励

> 最终审阅版 v1 · 2026-09-14。需求已收敛。用户于续接会话明确授权按最终规划进行本地实施与验证；历史“本轮只做规划”限制仅适用于上一轮。实施进度见 [progress.md](progress.md)，生产操作和外部发布仍需另行授权。

## Goal

让社区成员方便地捐献可用 API key，为公益站补充资源，并获得可追溯的一次性额度感谢；站长能够管理接收活动、查看捐献来源并避免重复发奖。

## Background

- 公益站服务于 Linux DO 社区，new-api 已接入社区登录；gpt-load 已承担上游分组与密钥管理。
- 用户强调捐献出于善意，产品以感谢社区成员为出发点。
- 研究基于本地 gpt-load `57965b94` 和 `D:/code/Claude code program/new-api` 的 `bc223d567`；证据见 [代码研究](research/codebase-findings.md)。未连接线上实例，生产版本与配置需在上线准备时核对。

## Requirements

- **R1 社区身份**：每笔有奖励的捐献对应实际登录的 new-api 用户，奖励发给该账号；沿用站点现有登录与账号状态规则，不另建用户体系或追加新的登录方式限制。
- **R2 密钥接收**：首批接收 Gemini AI Studio 普通 API key，并归入管理员指定的现有 gpt-load 分组；资源类型与调用能力按分组解析。
- **R3 活动配置**：管理员在 new-api 内设置对外显示名称、目标分组和开启状态；目标分组从已连接 gpt-load 的分组列表选择，不靠手工填写 ID。
- **R4 自动奖励**：每个首次通过校验且成功接收的非重复 key，按活动中配置的固定金额自动发放一次 new-api 永久额度，计入用户永久余额，不设到期时间；不按后续实际使用量追加结算。
- **R5 规划先行**：先完成需求、研究、技术方案和可执行任务，经审阅与明确授权后实施。规划收尾已完成，本次续接已获本地实施与验证授权；生产操作及外部发布另行确认。
- **R6 明确结果**：捐献人可查看本人逐项校验、接收和发奖状态及批次汇总，部分成功不能展示为全部成功。
- **R7 防止重复**：本站同一 key 不因更换用户、活动、分组或请求标识而再次获得奖励；并发提交和网络重试也只能产生一次接收资格和一次奖励。已在 gpt-load 库内的 key 不构成本次首次新增，不发新捐献奖励，也不冒认其原始捐献人。
- **R8 可恢复**：密钥已接收但奖励暂未到账时，保留可追踪记录并支持自动恢复，不要求用户重新交 key。处理中账号被禁用则暂停未发奖励，保留归属与原因，不绕过账号限制。
- **R9 身份与秘密保护**：普通用户不能指定收款用户 ID、实际入库组或奖励金额，也不能读取他人 key、管理接口或捐献记录；响应、普通日志与浏览器持久缓存不含完整 key 或集成凭据。
- **R10 规则可追溯**：受理时冻结规则与目标引用；关闭活动拒绝新批次，已受理批次按原规则处理。目标失效时显式报错，不静默取消奖励承诺或改投其他分组。
- **R11 站内入口**：new-api 顶部导航栏提供捐献入口，捐献行为关联现有登录用户。
- **R12 管理关联记录**：new-api 管理端提供类似日志的捐献记录，持久关联捐献用户、每个 key、目标分组、接收结果和奖励结果。已接收 key 后续失效、被禁用或从分组删除后，仍保留历史和防重复依据，不恢复其领奖资格。
- **R13 分组驱动**：活动显示名称由管理员自定义；渠道、上游地址、密钥格式及校验协议/模型复用所选 gpt-load 分组和既有渠道能力。new-api 不要求额外选择平台或重复填写上游参数，不从活动名称推断技术行为。
- **R14 校验先于奖励**：由后端使用本次提交的 key，按所选分组执行真实调用校验；仅格式合法、前端声明成功或其他 key 调用成功都不算通过。无效、结果不确定或未成功接收时不发奖。
- **R15 不限领奖数量**：首版不设置按用户或按日的领奖数量上限，也不增加对应配置项；同一用户提交不同的合格 key，分别按活动规则奖励。R7 的同 key 一次性资格继续生效。
- **R16 多行提交**：支持每行一个 key 的多行粘贴，一次选择一个活动并提交；每个 key 独立校验、接收、记录和发奖，失败项单独说明原因，不阻断其他合格项。
- **R17 不追回奖励**：已发放的永久奖励不因 key 后续失效、账号/密钥封禁、撤销或删除而扣回；捐献模块不提供追回奖励功能。
- **R18 页面风险提示**：在 key 输入区附近、提交前可见的位置显示下列小字；保持可读对比度和移动端换行，不增加强制确认弹窗或勾选门槛。

> 请勿使用主账号的 API key。捐献后的使用可能因平台风控或其他原因导致账号受限、封禁，或 key 失效，请确认能承担相关风险。

## Acceptance Criteria

以下实施验收标准已完成本地验证，逐项证据见 [最终验收](research/final-acceptance.md)。测试使用合成奖励数值，生产金额由管理员配置；不据此声称真实Google凭据或生产部署已经验证。

- [x] **AC1 → R1/R9**：已登录且符合参与条件的用户完成捐献后，记录和奖励归属其认证账号；篡改页面参数不能给其他账号发奖。
- [x] **AC2 → R2/R3/R4**：开启的活动接受指定类型 key，完成配置的真实调用校验后进入指定分组；关闭活动拒绝新提交。
- [x] **AC3 → R4/R6**：首次合格且成功接收的 key 按提交时冻结的活动固定额度发奖一次，用户永久余额正确增加并可查看到账记录。
- [x] **AC4 → R6/R7**：同一 key 换用户、活动、分组、请求 ID 重复提交，或两个请求并发争用时，至多一个请求取得接收资格，至多一次奖励入账。
- [x] **AC5 → R6/R8**：校验超时、上游限流、入库后进程重启、发奖响应丢失时，结果可查询并按已确定规则恢复。
- [x] **AC6 → R9**：普通用户响应、日志、错误信息和浏览器持久缓存不含完整 key 或管理凭据；本人记录以脱敏标识展示。
- [x] **AC7 → R10**：规则变更、目标组变化和活动关闭与处理中提交并发时，按明确的版本与状态规则处理。
- [x] **AC8 → R5**：页面位置、首批服务商、奖励模型及异常处置均经讨论确定，规划文档消除阻塞问题后再提交最终审阅。
- [x] **AC9 → R3/R11**：用户可从 new-api 顶部导航进入捐献页；管理员配置活动时能加载并选择 gpt-load 分组，保存后实际接收目标与所选分组一致。
- [x] **AC10 → R12/R9**：管理员可从捐献记录查到用户及对应的 key 脱敏标识、gpt-load 凭据 ID、目标组与结果；普通用户不能读取他人记录。
- [x] **AC11 → R2/R3/R13**：管理员填写 `gemini aistudio free key` 并选择已有目标组，即完成该活动的资源配置；无需另填平台、上游地址和测试模型，实际校验遵循所选组的现有解析规则。修改显示名称不会改变渠道、校验或入库目标。
- [x] **AC12 → R7/R12**：已领奖 key 失效、禁用或删除后再次提交，仍不发第二次奖励；管理员能查到原用户、原接收结果与奖励记录。普通日志清理不影响此行为。
- [x] **AC13 → R4/R14**：格式正确但上游拒绝的 key、校验超时/限流和接收失败均不发奖；验证过程中不得切换组内其他 key 来完成校验。
- [x] **AC14 → R4/R7/R15**：同一用户在同一天提交多个不同的合格 key，分别取得固定奖励，不因历史领奖数量被拒绝；重复 key 仍不奖励，配置页没有每日领奖数量上限字段。
- [x] **AC15 → R4**：奖励进入永久额度，不新增或占用签到临时额度桶；跨日和签到过期清理不会使未使用的捐献奖励失效，也不受当天签到类型影响。
- [x] **AC16 → R6/R7/R16**：多行内容支持 LF/CRLF、忽略空行、去除 key 首尾空白并保留大小写；批次内重复 key 只取得一次资格，结果可以定位原输入行。
- [x] **AC17 → R4/R6/R16**：一批中混合新有效 key、无效 key、重复 key 和校验暂不确定项时，独立显示结果，只给成功新增项发固定永久额度；整个批次重试不重复发奖。
- [x] **AC18 → R2/R4/R7**：提交已经存在于 gpt-load 的 key，返回已有资源结果、不增加奖励、不改写原来源；新 key 与已有 key 混在同批时不影响新 key 的正常处理。
- [x] **AC19 → R4/R12/R17**：发奖后 key 被标记失效、禁用、撤销或删除，用户不产生捐献奖励追扣，原历史保留，同 key 仍不能再次领奖。
- [x] **AC20 → R18**：桌面和移动端提交前均能读到主账号、封号/封 key 风险提示，文案支持项目 i18n；无需额外弹窗或确认勾选。

## Out of Scope

- 现金支付、提现、排行榜、邀请分成、多公益站统一结算。
- gpt-load 独立捐献门户、新用户体系或新增跨站登录。
- OAuth/订阅凭证、new-api 独立平台适配、Google 项目身份核验及余额估价。
- 后续用量结算、限时奖励、奖励追扣、领奖数量/累计业务奖励配额管理。

## Known Limits

- Gemini 不同 key 可能共享项目配额；本站按 key 去重，不承诺识别同项目的多个 key。用户已选择不添加领奖上限。
- 历史已彻底删除且没有记录的旧 key 无法追溯；长期防重复依赖功能上线后完整保存的业务记录与指纹密钥。
- 生产连通性、实际分组及模型配置尚未核对。实现细节需遵守已定契约；不改变用户行为的内部迁移编号、组件拆分和重试时间参数交由对应子任务确定。
